# Spec — Internacionalización (i18n) y área TEXTOS del editor

Estado: **propuesta / análisis** (sin implementación). Objetivo: publicar en
Steam en al menos **inglés (en)**, **español rioplatense (es-AR, fuente)** y
**chino simplificado (zh-Hans)**, con todo texto visible al jugador editable
desde el editor admin, a mano o con borrador de traducción automática.

## 1. Inventario actual (estimaciones por grep, nov-2026)

Patrón: literales `'Mayúscula…'` de ≥3 caracteres en `.dart`. Incluye falsos
positivos (ids, claves de log), así que tomar como orden de magnitud.

| Zona | Literales aprox. | Notas |
|---|---|---|
| `features/world` | ~1580 | HUD, interacción, carteles, oficios |
| `features/combat` | ~1500 | log de combate, menús, estados, tooltips |
| `features/admin` | ~1360 | editor (no prioritario: herramienta interna) |
| `features/inventory` | ~1280 | grilla, detalle, comparadores |
| `features/build_planner` | ~470 | |
| `features/characters` | ~390 | |
| `features/settings` | ~300 | OPCIONES |
| `lobby`, `run`, `endgame`, `missions`, `passive_tree` | 130–190 c/u | |
| `screen_editor`, `ascension`, `bestiary`, `achievements`, `tutorial` | 50–120 c/u | |
| `game_engine/` (≈46 catálogos en `data/`) | ~3300 | nombres/descr. de ítems, clases, skills, ults, pasivas, misiones, zonas, biomas, enemigos, afijos, logros, diálogos NPC (`npc_talk…`) |

- **Assets de datos**: `assets/data/npcs/npcs.json` (diálogo NPC), `assets/data/ults/*` (51),
  `assets/data/enemy_ults/*` (37), `assets/layouts/*.screen.json` (9, rótulos de pantallas).
- **Notas de versión**: panel de novedades alimentado por texto en repo (Dart/MD);
  se decide **no traducir el historial viejo**; desde la v1.0 las notas tienen en/es/zh.
- **Texto generado**: interpolaciones `'$n de daño'`, `'Nivel $lvl'`, plurales a mano
  (`n == 1 ? … : …`), porcentajes y decimales con formato fijo. Solo ~17 usos de
  `Intl/plural/DateFormat`; no hay infraestructura i18n.
- **Texto en sprites**: los `assets/fx/*` y sprites son mayormente icónicos; hay que
  auditar a mano carteles/logos con letras (logo del título). Regla: ningún texto
  nuevo dentro de imágenes; el logo tiene variante por idioma si contiene palabras.
- **Total estimado a traducir al jugador** (sin admin): ~10–12k cadenas de origen,
  de las cuales ~60 % viven en catálogos de `game_engine`.

## 2. Fuentes

Actuales (`pubspec.yaml`, todas OFL 1.1): **PressStart2P** (títulos), **VT323**
(cuerpo retro), **AtkinsonHyperlegible** (modo accesible); `RetroType` /
`RetroTheme` deciden familia (~51 usos). Consolas aparece en el editor.

Cobertura:
- PressStart2P: latín básico + parcial Latin-1; **faltan mayúsculas acentuadas
  (ej. "Í")** y no tiene CJK. VT323: Latin-1 razonable, sin CJK. Atkinson: latín
  extendido, sin CJK.
- Acción inmediata: test de glifos (ver §6) que recorra los catálogos `es`/`en` y
  falle si un carácter no está en el `cmap` de la fuente asignada.

CJK pixel (verificar licencia en el repo oficial antes de integrar; anotar en
`assets/fonts/OFL-*.txt`):
- **Fusion Pixel Font** (12px, zh-Hans/zh-Hant/ja/ko): OFL 1.1 — **recomendada**
  para cuerpo y títulos en zh. Apta para uso comercial y embebida en el juego.
- **Zpix (最像素)**: revisar: su licencia no ha sido OFL en todas las versiones
  (históricamente con restricciones comerciales) → solo si la versión vigente lo permite.
- **GNU Unifont**: OFL 1.1 / GPL dual; cobertura total pero 16px y estética tosca →
  fallback de último recurso.
- Alternativa no pixel: **Noto Sans SC** (OFL) para el modo accesible en zh.

Estrategia:
- `RetroType` resuelve familia por locale: `zh` → Fusion Pixel (títulos y cuerpo),
  con `fontFamilyFallback: [FusionPixel, NotoSansSC]` también en es/en para nombres
  de jugadores en CJK que lleguen por red.
- CJK a 12px necesita tamaño múltiplo de 12 (12/24) para quedar nítido; ajustar
  `height` (line-height ~1.25) y tokens tipográficos del design system por locale.
- Ancho: el inglés ocupa ~igual o menos que el español; zh menos ancho pero más alto.
  El alemán no está en alcance pero planificar +30 %.
- **Regla sin truncado**: ningún texto de jugador usa `TextOverflow.ellipsis`
  silencioso; los contenedores usan `FittedBox`/wrap o crecen; el editor marca
  cadenas que exceden el presupuesto (§4). Respetar tope de tooltips existente.
- Peso: Fusion Pixel ~ varios MB; subsetear con `pyftsubset` al set de caracteres
  realmente usado por el catálogo zh en el build de release.

## 3. Arquitectura

Decisión: **tablas propias (JSON) + servicio `Strings` en Dart puro**, no ARB/gen-l10n.
Motivo: gen-l10n genera código desde ARB en tiempo de compilación y depende de
Flutter; el editor necesita editar en caliente y `game_engine` debe resolver
textos sin Flutter. Sí se usa sintaxis **ICU MessageFormat** dentro de los valores.

Estructura:
```
lib/core/i18n/                 (Dart puro)
  locale_id.dart               enum LocaleId { esAR, en, zhHans }
  string_key.dart              typedef/extension type StringKey(String)
  strings.dart                 abstract class Strings { String t(StringKey k, [Map args]); }
  catalog_strings.dart         impl: tablas en memoria + fallback es-AR + ICU (plural/select)
  icu_formatter.dart           subset ICU: {n, plural, one{} other{}}, {x, select, …}, números
lib/features/settings/...      selector de idioma en OPCIONES (+ "Automático (Steam)")
assets/i18n/
  es-AR/<domain>.json          fuente; dominios: ui.common, ui.combat, items, skills, npcs, lore...
  en/<domain>.json
  zh-Hans/<domain>.json
  meta/<domain>.json           por clave: contexto, feature, maxLen, screenshot, hash de la fuente
```
Formato por entrada en locales destino:
`"items.sword_rust.name": {"text": "Rusty Sword", "status": "reviewed", "srcHash": "a1b2"}`.

Reglas:
- **Claves estables, en inglés, jerárquicas**: `<domain>.<id>.<field>`
  (`skills.fireball.desc`, `ui.inventory.equip`).
- **Catálogos de `game_engine`**: los modelos guardan `id` y dejan de tener
  `name/description` literales; el nombre se deriva (`items.${id}.name`). Durante la
  migración, un extractor copia el literal actual a `es-AR` y reemplaza por la clave.
- Presentación: `context.t('ui.inventory.equip')` vía Riverpod provider que expone
  `Strings` del locale activo; `game_engine` recibe `Strings` por inyección cuando
  necesita texto (log de combate) — preferible que el engine emita **eventos
  estructurados** (`DamageEvent(actor, amount)`) y la UI los formatee.
- **Red**: nunca se envía texto. Se envían ids/claves + argumentos; cada cliente
  renderiza en su idioma → co-op con idiomas mezclados funciona. Nombres de jugador
  son el único texto libre (fallback de fuente CJK).
- **Fallback**: locale activo → es-AR → la clave misma (visible en dev, y un test lo
  impide en release). Texto `status: machine` se muestra solo si la flag
  `allowMachineText` del flavor está activa (dev/beta), nunca en release.
- Números: `NumberFormat` por locale (separador decimal es-AR `,`). Fechas casi no
  hay; si aparecen, ICU `date`.
- Flavors (`lib/app/flavors/`) eligen locales habilitados vía `FeatureFlags`.

## 4. Editor: área TEXTOS

Nueva entrada en `EditorArea` (`admin_app.dart`): **TEXTOS**. Respeta reglas UI:
grilla con detalle a la derecha, filtros/subtabs en vez de secciones apiladas.

- Grilla **clave × idiomas** (columnas es-AR / en / zh-Hans), virtualizada.
- Filtros: dominio/feature, estado (`missing`, `outdated`, `draft`, `machine`,
  `reviewed`), búsqueda por clave y texto en cualquier idioma, "excede largo".
- **Outdated**: si cambia el texto fuente, su hash ya no coincide con `srcHash` del
  destino → marcado desactualizado.
- Panel derecho: edición inline con preview en la fuente real del juego al tamaño de
  destino, contexto (`meta`: descripción, dónde aparece, captura opcional de
  `docs/release_shots`), contador y aviso de `maxLen`, placeholders ICU validados
  (mismas variables que la fuente).
- Estados: `draft` (humano sin revisar), `machine`, `reviewed`. Solo `reviewed`
  entra al build de release (lo verifica un test).
- Integración: el editor de NPC y el de pantallas dejan de guardar texto suelto y
  escriben claves; editar el texto en esos editores escribe en `es-AR/<domain>.json`.
- Export/import CSV/XLIFF para traductores externos.

### Traducción automática (opcional, borradores)

Recomendación **local primero** (gratis, privado, offline):
1. **Argos Translate** (MIT, modelos OPUS-MT) — es→en directo bueno; es→zh suele
   pivotar por en (calidad menor).
2. **NLLB-200 distilled 600M** vía CTranslate2/ONNX — mejor para zh; licencia de
   pesos **CC-BY-NC**: aceptable para generar borradores internos que luego se
   revisan, pero confirmarlo con el dueño; si molesta, usar OPUS-MT.
3. **LibreTranslate** self-hosted (AGPL, usa Argos) si se prefiere una API HTTP local.
- APIs con free tier (DeepL Free, etc.) quedan como opción manual: envían texto a
  terceros y tienen cuotas.
- Runner: script Python en `tools/mt/` invocado por el editor (proceso local,
  JSON por stdin/stdout); el editor nunca embebe el modelo.
- **Glosario** `assets/i18n/glossary.json`: términos de lore con traducción fija
  por idioma (Ecos, Torre del Tiempo, oficios, nombres de clases/elementos) o
  marcados "no traducir". Se protegen con placeholders antes de MT y se restauran
  después; el editor avisa si una traducción no usa el término del glosario.
- Todo resultado MT queda `status: machine`; nunca se publica sin pasar a `reviewed`.

## 5. Steam

- Detectar idioma por defecto con Steamworks `ISteamApps::GetCurrentGameLanguage()`
  (`"latam"`/`"spanish"` → es-AR, `"english"` → en, `"schinese"` → zh-Hans); si no
  hay Steam, idioma del SO; el usuario puede sobreescribir en OPCIONES.
- Store: declarar por idioma "Interfaz / Audio / Subtítulos" con verdad (sin voces
  → solo Interfaz + Subtítulos). Página, descripción, capturas y tráiler localizados
  por idioma (capturas desde `docs/release_shots` por locale).
- Checklist: idiomas declarados en Steamworks; build con fuentes zh incluidas;
  logros (nombres/descr.) cargados por idioma en Steamworks; textos legales/EULA;
  nombres de depósitos; pruebas con cliente Steam en chino; notas de parche en los 3.
- China continental: esta spec no cubre requisitos regulatorios de distribución allá.

## 6. Plan de migración

| Fase | Contenido | Esfuerzo |
|---|---|---|
| 0 | `core/i18n` (Strings, ICU subset, fallback), carga de assets, selector en OPCIONES, detección Steam | 3–4 días |
| 1 | Lint: test `test/i18n/no_hardcoded_strings_test.dart` que escanea `lib/features/**/presentation` y `game_engine/data` y falla ante literales nuevos con letras dentro de `Text(`, `tooltip:`, `label:` etc. (allowlist inicial = baseline generado; solo puede bajar) + test de glifos + test de claves faltantes/placeholders | 1–2 días |
| 2 | Extractor semiautomático (script) por feature: literal → clave + entrada es-AR. Orden: OPCIONES, menú/lobby, combate, inventario, world | 2–3 semanas |
| 3 | Catálogos de `game_engine` a ids + claves; log de combate a eventos estructurados | 1–2 semanas |
| 4 | Área TEXTOS del editor + integración NPC/pantallas + glosario | 1–1,5 semanas |
| 5 | Runner MT local + borradores en/zh | 3–4 días |
| 6 | Fuentes zh (Fusion Pixel, subset), ajuste de layouts sin truncado, revisión humana en/zh | 2–3 semanas (+ traductor) |
| 7 | Steam: store, logros, QA con cliente en cada idioma | 3–5 días |

Riesgos:
- Volumen (~10k cadenas) → la revisión humana zh es el cuello de botella real; MT
  solo acelera.
- Concatenaciones y género gramatical en el español fuente (`'Nivel ' + n`) rompen
  el orden en otros idiomas → toda cadena con variables debe ser un único mensaje ICU.
- Layouts calibrados al ancho de PressStart2P; zh cambia alto de línea.
- Licencias de fuentes/modelos (Zpix, NLLB) a verificar antes de enviar build.
- Divergencia entre editor y código si conviven literales y claves durante mucho
  tiempo → el lint con baseline decreciente lo controla.
- Tamaño de build por fuentes CJK → subset.
